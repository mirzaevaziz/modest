# BA, DEV, and QA Roles in the SDLC

Three roles carry a change from "someone wants something" to "it runs in production and stays correct." They overlap on purpose: the handoffs are where defects are born, so each role reaches one step into the next one's territory.

---

## Business Analyst (BA)

**Owns:** the problem definition. What should be built, for whom, and why — and how anyone will know it's done.

### Responsibilities by phase

| Phase | BA does |
|---|---|
| Discovery | Talks to stakeholders and users, finds the real problem behind the requested feature, maps the current process |
| Requirements | Writes user stories / use cases, defines acceptance criteria, models data and business rules |
| Design | Reviews proposed solution against business intent, flags gaps and edge cases |
| Development | Answers questions, resolves ambiguity, adjusts scope when reality intervenes |
| Testing | Confirms delivered behavior matches intent (UAT support), coordinates business sign-off |
| Release | Prepares user docs, training, rollout communication |

### Key artifacts
- Business requirements document / product backlog items
- User stories with **acceptance criteria** — the shared contract between BA, DEV, and QA
- Process flows (BPMN, swimlanes), data dictionaries, business rules catalog
- Wireframes or click-through mockups (often jointly with design)

### A good story
```
As a warehouse supervisor
I want to see suppliers filtered by active status
So that I don't order from a delisted vendor

Acceptance criteria:
- Given the supplier list, when I select "Active only", then only suppliers with Status = Active are shown
- Given no active suppliers exist, then an empty-state message appears
- The filter persists across page reloads within the session
```

### Failure modes
- Requirements written as solutions ("add a dropdown") instead of needs — locks out better designs
- Acceptance criteria that are untestable ("system should be fast")
- Silent scope growth during development because ambiguity is resolved verbally

## Developer (DEV)

**Owns:** the solution. Turning agreed requirements into working, maintainable, verified software.

### Responsibilities by phase

| Phase | DEV does |
|---|---|
| Requirements | Reviews stories for feasibility, estimates, raises technical constraints early |
| Design | Chooses architecture, data model, APIs; writes technical design where the change is non-trivial |
| Development | Implements, writes unit and integration tests, code reviews peers |
| Testing | Fixes defects, reproduces reported issues, supports QA with test data and environments |
| Release | Migrations, deployment, feature flags, rollback plan |
| Operations | Monitors, handles incidents, pays down technical debt |

### Key artifacts
- Source code and automated tests
- Technical design notes / ADRs for decisions that are expensive to reverse
- API contracts (OpenAPI, schemas) — QA and front-end consumers depend on these
- Pull requests, review comments, migration scripts

### Quality practices that belong to DEV, not QA
- Unit tests for logic branches; integration tests across the real boundary (DB, HTTP)
- Input validation at trust boundaries; error handling that doesn't lose data
- Code review for readability and correctness, not style bikeshedding (automate style)
- Definition of Done includes: tests pass, reviewed, deployable, observable

### Failure modes
- Starting to code before acceptance criteria are agreed — "it works" against the wrong target
- Treating QA as the safety net for logic the developer never tested
- Design decisions made silently that contradict business rules the BA captured

## Quality Assurance (QA)

**Owns:** confidence. Evidence about whether the software does what was agreed and behaves under conditions nobody asked about.

QA is not "the people who click the buttons at the end." QA starts at requirements — the cheapest defect to fix is one caught in a story review.

### Responsibilities by phase

| Phase | QA does |
|---|---|
| Requirements | Reviews stories for testability, asks the edge-case questions ("what if two users do this at once?") |
| Design | Plans test approach, identifies risk areas, defines test data and environment needs |
| Development | Writes test cases and automation in parallel with the code, tests early increments |
| Testing | Functional, regression, integration, performance, security, accessibility, exploratory testing |
| Release | Smoke tests in staging and production, go/no-go input |
| Operations | Verifies fixes, grows the regression suite from real escaped defects |

### Test levels and who owns them

| Level | Typical owner |
|---|---|
| Unit | DEV |
| Integration / component | DEV (QA reviews coverage) |
| System / end-to-end | QA |
| Acceptance (UAT) | BA + business users, QA facilitates |
| Non-functional (load, security, accessibility) | QA, often with specialists |

### Key artifacts
- Test plan and test strategy (risk-based: test most where failure hurts most)
- Test cases traceable back to acceptance criteria
- Automated regression suite
- Defect reports: steps to reproduce, expected vs. actual, environment, severity vs. priority

### A good defect report
```
Title: Supplier filter resets after pagination
Environment: staging, build 2026.08.14-3, Chrome 128
Steps:
  1. Open Suppliers, set filter to "Active only"
  2. Go to page 2
Expected: filter still applied, only active suppliers listed
Actual:   filter cleared, all suppliers listed
Severity: Major (wrong data shown)  Priority: High (blocks story ACC-214)
```

### Failure modes
- Testing only the happy path described in the story
- Automation that tests implementation detail and breaks on every refactor
- Reporting defects without reproduction steps — turns into a DEV scavenger hunt

## How the three interlock

```
BA ──requirements + acceptance criteria──▶ DEV ──build──▶ QA ──verify──▶ Release
 ▲                                          │              │
 └────────ambiguity, scope questions────────┘              │
 ▲────────────────defects, gaps─────────────────────────────┘
```

**The Three Amigos.** Before a story is picked up, BA, DEV, and QA discuss it together for 15–30 minutes:
- BA states the intent and the rules
- DEV raises feasibility, cost, and technical constraints
- QA raises edge cases, data conditions, and how each criterion will be proven

Output: a story all three agree is clear, feasible, and testable. This single meeting removes more rework than any downstream process.

### Shared ownership
| Concern | Not owned by one role |
|---|---|
| Quality | Everyone. QA measures it; DEV builds it in; BA defines what "good" means |
| Scope | BA proposes, DEV costs, QA flags the risk of cutting |
| Definition of Done | Agreed by all three, enforced by all three |

### Traceability chain
```
Business need → Requirement → Acceptance criterion → Test case → Test result → Release note
```
Every link should be navigable in both directions. If a test exists with no criterion behind it, ask why it's being run. If a criterion has no test, it isn't verified.

## Role emphasis by methodology

| | Waterfall | Agile / Scrum | DevOps-heavy |
|---|---|---|---|
| **BA** | Big upfront requirements document, formal change control | Continuous backlog refinement, often merges with Product Owner | Feeds a fast, small-batch flow; heavier on outcome metrics |
| **DEV** | Builds to a frozen spec, long integration phase | Cross-functional team member, owns tests and often deploys | Owns build-run: "you build it, you run it," on-call |
| **QA** | Separate phase and often a separate department | Embedded in the team from day one, shift-left | Quality engineering: automation in the pipeline, quality gates as code |

**Shift-left** is the common direction across all three: move requirement clarification, testing, and security checks as early as possible, because defect cost rises sharply the later it is found.

## Anti-patterns across the boundaries

| Anti-pattern | Symptom | Fix |
|---|---|---|
| Throw over the wall | Each role finishes and disappears | Three Amigos; shared Definition of Done |
| QA as a gate, not a partner | QA sees the feature for the first time in test | QA in refinement, test cases written alongside code |
| BA as a ticket typist | Stories restate stakeholder wording verbatim | BA is accountable for understanding the *problem* |
| Ping-pong defects | "Works on my machine" / "not a bug, by design" | Acceptance criteria are the referee; unclear criteria go back to BA |
| Manual regression sprawl | Test cycle grows longer every release | Automate the stable regression path, keep manual for exploratory |

## Quick reference

| | BA | DEV | QA |
|---|---|---|---|
| **Core question** | Are we building the right thing? | Are we building it well? | Did we actually build it, and does it hold? |
| **Primary artifact** | Acceptance criteria | Working code + tests | Test results + defect reports |
| **Starts at** | Discovery | Refinement | Refinement |
| **Main risk if weak** | Wrong product | Unmaintainable product | Undetected breakage |
