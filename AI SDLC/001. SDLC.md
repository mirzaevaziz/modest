## What SDLC Is

SDLC stands for **Software Development Life Cycle** — the process the software industry uses to analyze, develop, and test software.

It is a framework that organizes the core development processes so a team can reach the maximum achievable quality within real constraints:

- Budget
- Timeline
- Team expertise

The point is not ceremony. The point is that quality is bounded by those constraints, and a life cycle makes the trade-offs explicit instead of accidental.

---

## The Six Phases

### 1. Planning

Business stakeholders meet to identify:

- Who the users are
- How the software will be used
- What data it must process

**Deliverable:** a **Requirement Specification** document covering functional requirements, business requirements, client requirements, and user requirements.

### 2. Requirement Analysis

Senior team members and industry experts define what the software fundamentally *is* and how it positions against competitors. This is the critical phase — errors here propagate through everything downstream.

**Deliverables:**
- **System Requirements Specification (SRS)**
- Risk identification plan
- Quality assurance baselines

### 3. Design

Architects turn the SRS into a technical plan.

**Deliverable:** the **System Design Specification (SDS)**, also called the **Design Document Specification (DDS)**. It outlines:

- Architectural modules
- Data flow diagrams
- Communication flows
- Third-party integrations

Stakeholders review the SDS against four criteria: **risk, robustness, modularity, and budget**.

### 4. Implementation

Engineers build the software modules from the SRS and SDS.

Speed and quality in this phase depend on three inputs — none of them created in this phase:

- The expertise of the analysts who wrote the requirements
- The quality of the documentation
- The experience of the developers

Weak SRS or SDS shows up here as slow, low-quality implementation.

### 5. Testing and Integration

Testing runs in cycles, alternating between:

- Automated unit and functional tests
- Human acceptance testing

The cycle repeats until the software reaches the required quality standard.

### 6. Maintenance

Software goes to alpha/beta or stable release. Feedback is collected and analyzed, and that analysis feeds the **next iteration of the SDLC** — new features or bug fixes.

The life cycle is a loop, not a line: maintenance feeds planning.

---

## Phase Summary

| # | Phase | Main deliverable |
|---|---|---|
| 1 | Planning | Requirement Specification (functional, business, client, user) |
| 2 | Requirement Analysis | SRS + risk plan + QA baselines |
| 3 | Design | SDS / DDS (modules, data flows, integrations) |
| 4 | Implementation | Working software modules |
| 5 | Testing and Integration | Software at required quality standard |
| 6 | Maintenance | Alpha/beta/stable release + feedback for next cycle |

## SDLC Models

Six primary approaches:

- **Waterfall**
- **Agile**
- **Iterative**
- **Spiral**
- **Rapid Application Development (RAD)**
- **Prototyping**

---

## Choosing a Model

"One size fits all" fails. Organizations should **combine** methodologies according to the specific conditions of a project rather than rigidly following a single framework.

> "The correct choice of SDLC in any specific project can only be made by analyzing the project and also the SDLC itself."

Two things follow from that:

1. Methodology selection comes **before** development planning, not after.
2. Choosing well requires understanding both the project *and* the model — knowing Agile is not enough if you do not know why this project fits it.
